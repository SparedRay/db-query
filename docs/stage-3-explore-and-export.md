## 0. The rule this whole stage obeys

> **Nothing generated is ever executed.** Every action in this stage writes SQL
> into an editor tab and stops. The user reads it, decides, and runs it.

Stated by the user up front, and it is load-bearing rather than a preference:
half the actions here are `DROP`. It also simplifies the design — generated SQL
never touches `AssertSqlSafe`, because it never reaches a connection. It is text
in a text editor until a human presses Ctrl+Enter.

The one place this needs care is **export**, which does re-read data. See §4.

## 1. Scope

### In scope

**Schema actions**
- Double-click a table or view → **new tab** containing `SELECT * FROM …  LIMIT n`
- Right-click a table/view → Select, Drop, and the obvious neighbours
- Right-click a column → Drop
- Right-click a schema → Drop
- Routines (procedures and functions) shown **separately** from tables and views
- Double-click a routine → append a `CALL` / `SELECT fn(…)` snippet to the
  **current** tab
- Right-click a routine → Append, Examine (full re-creation script), Drop

**Export**
- Result set → CSV file
- Result set → `INSERT` script, optionally preceded by `CREATE TABLE`
- Selected rows and/or columns → clipboard, with or without a header row

### Explicitly out of scope
- Editing data in the grid. Read-and-generate only; a writable grid is its own
  stage with its own safety story.
- Export to Excel/Parquet/JSON. CSV and SQL cover the ask; more formats are a
  small addition later once the export plumbing exists.
- Triggers and events in the tree. Same mechanism as routines, no new thinking —
  worth adding, not worth blocking this stage on.
- Import. Strictly harder than export and unrelated to the ask.

## 2. Corrections to the plan as described

Four things in the request need adjusting before implementation, three of them
because MySQL disagrees.

### 2.1 MySQL has no `CREATE OR REPLACE` for routines

The request asks that Examine open the definition "on a Create or replace".
That syntax is MariaDB and PostgreSQL; **MySQL 8 does not support
`CREATE OR REPLACE PROCEDURE` or `... FUNCTION`.** `SHOW CREATE PROCEDURE`
returns a bare `CREATE PROCEDURE`, which fails with *"routine already exists"*
if you run it back.

So Examine will emit the re-runnable equivalent:

```sql
DROP PROCEDURE IF EXISTS `db`.`name`;
DELIMITER $$
CREATE PROCEDURE `db`.`name`(...)
BEGIN
  ...
END$$
DELIMITER ;
```

That is the intent of "create or replace", spelled the way MySQL accepts. It
also means the generated script is *destructive if run* — which is exactly why
the never-auto-run rule matters, and why the `DROP` line is on screen rather
than hidden.

**This interacts with our splitter:** `DELIMITER` makes `split.rs` bail out to a
single span, and `auto_limit` is disabled for such a script. Both are already
the right behaviour — a routine body must go to the server whole — but it means
an examined routine runs as one statement with one result. Worth knowing, not
worth changing.

### 2.2 "Whatever limit we have by default" does not exist yet

There is no browse limit. What exists is `MAX_ROWS = 5000`, the **safety
ceiling** applied by the auto-limit checkbox to protect the UI from a runaway
`SELECT *`. Reusing it as the double-click default would mean every table peek
pulls 5000 rows.

Proposal: introduce an explicit, separate **browse limit, default 1000**,
settable in the UI, used only for generated `SELECT` statements. It is a
different thing from the safety ceiling and should not share a number with it —
one is "what I want to look at", the other is "what will not wedge the app".

Generated SQL will carry an explicit `LIMIT`, so `auto_limit` correctly leaves
it alone (it already skips statements with a top-level `LIMIT`).

### 2.3 Export is bounded by what was fetched

A result set in memory is already capped — `MAX_ROWS` per statement, and
`truncated: true` says so. "Export to CSV" on a truncated result would silently
write 5000 rows and look like the whole table. That is the same class of failure
as the empty schema tree in Stage 0: no error, wrong answer.

So export offers two honest paths, and **names which one it is doing**:

| Path | What it exports | When |
|---|---|---|
| **Export shown rows** | exactly the grid contents | always available, instant |
| **Re-run and export all** | re-executes the statement with no limit, streams to file | only when the statement is re-runnable |

If a result is truncated and the user picks the first, the UI says how many rows
it wrote and that there were more. **Never a silent partial export.**

The second path cannot always be offered: a statement whose result came from a
script with `USE`, temp tables, or session state may not reproduce standalone.
When we cannot guarantee it, we do not offer it.

### 2.4 Double-click is inconsistent between tables and routines — deliberately

Tables open a **new tab**; routines append to the **current** tab. That is what
was asked for and it is defensible: browsing a table is a fresh task, calling a
procedure is usually a step inside a script you are already writing. Recording
it so it reads as a decision rather than an accident.

## 3. Architecture decisions

### 3.1 All SQL generation lives in Rust

Identifier quoting and literal escaping are the two places this stage can
produce a *wrong or dangerous* script, and both must have exactly one
implementation. Stage 1 already taught this lesson: cursor-statement logic was
duplicated in TypeScript and drifted until a dead-code warning caught it. The
fix was `statement_at_cursor` — one splitter, one source of truth.

Same shape here. The frontend asks for text and inserts it:

```
generate_select(db, table, limit)      -> String
generate_drop(target)                  -> String
generate_call(db, routine)             -> String
generate_routine_ddl(conn, db, name)   -> String   (needs the server)
```

The frontend never concatenates SQL.

### 3.2 Identifier quoting

Every generated identifier is backtick-quoted, with embedded backticks doubled:

```
`orders`          `weird``name`          `db`.`table`
```

Always quoted, never conditionally — "quote only if it needs it" requires a
keyword list that will be wrong for one MySQL version or another. Unconditional
quoting is always correct and the cost is cosmetic.

### 3.3 Literal escaping is the risk of this stage

Generating `INSERT`s means turning decoded values back into SQL literals, and
the decode already lost information on purpose. From `decode.rs`, a `BIGINT`
beyond 2^53 and a `DECIMAL` both arrive as `CellValue::Text` so JavaScript
cannot round them — if the generator quotes them because they are text, the
resulting script inserts strings into numeric columns.

So the generator is driven by **`ColumnMeta.sql_type`, not by the runtime type
of the cell.** That is what the column metadata is for, and it is already
carried on every result.

| `sql_type` family | Emitted as |
|---|---|
| numeric (`INT`, `BIGINT`, `DECIMAL`, …) | bare, unquoted, verbatim text |
| `NULL` cell, any type | `NULL` — never `''`, never `'NULL'` |
| binary (`BLOB`, `BINARY`, `GEOMETRY`) | `0x…` hex literal |
| temporal | quoted string |
| everything else | quoted string, escaped |

String escaping handles `\`, `'`, `"`, NUL, `\n`, `\r`, Ctrl-Z — the set MySQL
actually requires. This gets a hostile test suite; see §5 Phase 2.

### 3.4 CSV is hand-rolled

Consistent with the precedent already set in `grid.ts` ("hand-rolled
virtualization rather than a library… keeps the dependency surface and the
licence audit small"). CSV *writing* is genuinely small — RFC 4180 quoting is a
handful of rules — and unlike parsing it has no ambiguity to get wrong.

Decisions to make explicit, because every one of them bites someone:

- **NULL vs empty string.** These are different values and CSV cannot express
  the difference. Default: `NULL` → empty field, with a toggle to write the
  literal `NULL`. Whatever we pick, it is documented in the export dialog.
- **CRLF line endings**, per RFC 4180, for Excel's benefit.
- **UTF-8 BOM**, optional, default on. Without it Excel mangles non-ASCII. With
  it, some Unix tools show `﻿`. It is a real trade-off, so it is a toggle.
- **Quote when needed**, not always: field contains `,` `"` CR or LF.
- **No formula guard by default.** A field starting `=` `+` `-` `@` is a CSV
  injection vector in spreadsheets. Offer a "prefix with `'`" toggle rather than
  silently altering the user's data — a SQL client that quietly changes exported
  values is worse than one that warns.

### 3.5 Routines need two information_schema queries

`information_schema.routines` gives name, type and return type;
`information_schema.parameters` gives the argument list needed for a useful
`CALL` snippet. Both filtered by schema, both aliased — the Stage 0 rules apply
unchanged (MySQL 8 uppercases information_schema column names, sqlx matches
case-sensitively, unaliased columns silently drop every row).

Cached per database alongside tables, in the existing `DbSchema`.

`SHOW CREATE PROCEDURE` needs privileges the user may not have. Failure must
degrade to a readable message, not an empty tab.

### 3.6 The context menu becomes shared

`connections.ts` already owns a context menu that learned three lessons the hard
way: dismiss on `mousedown` kills the button's `click`, Escape must close it,
and it must be clamped to the viewport. The tree needs the same thing.

Extract to `src/menu.ts` — the same move `choose()` made into `src/dialog.ts`,
for the same reason. One menu implementation, so the next fix lands everywhere.

### 3.7 Clipboard access is verified, not assumed

`window.confirm` cost us a silently-dead delete button in Stage 2 because Tauri
intercepted it. Clipboard is the same shape of risk: `navigator.clipboard` needs
a secure context and a user gesture, and a Tauri custom-protocol page may or may
not qualify.

**First task of Phase 5 is a five-minute empirical check**, not a design
decision: does `navigator.clipboard.writeText` work in our webview? If yes, no
dependency. If no, add `tauri-plugin-clipboard-manager` (MIT OR Apache-2.0 —
verify at the time, per the standing licensing rule). Either way we find out by
running it.

## 4. Backend command surface

New commands, all pure text generation except the last three:

```
list_routines(connection_id, db)              -> Vec<RoutineRef>
routine_ddl(connection_id, db, name, kind)    -> String

generate_select(db, table, limit)             -> String
generate_drop(target: DropTarget)             -> String
generate_call(connection_id, db, routine)     -> String

export_csv(tab_id, statement_index, opts)     -> ExportOutcome
export_inserts(tab_id, statement_index, opts) -> ExportOutcome
export_rerun(tab_id, statement_index, opts)   -> ExportOutcome   (streaming)
clipboard_text(rows, columns, opts)           -> String
```

`RoutineRef { name, kind: Procedure | Function, returns: Option<String>, params: Vec<Param> }`

`DropTarget` is an enum — `Schema { db }`, `Table { db, name }`,
`View { db, name }`, `Column { db, table, name }`, `Routine { db, name, kind }` —
so the generator cannot be handed a half-specified target.

Export writes through the existing `files::write_atomic` and the Rust-side
native save dialog, matching Stage 1: file I/O stays in Rust, `tauri-plugin-fs`
stays absent.

### Phase 1 — what shipped (2026-09-05)

Routine introspection, routine DDL, and the identifier quoter the rest of the
stage builds on. **169 tests pass** (115 unit + 3 fixture + 46 live + 5 keychain).

**The fixture gained routines** — `top_spenders` (a procedure with two
parameters), `order_count` (a function), and `ping_poc` (no parameters, because
an empty parameter list is a distinct code path in call generation).

#### Correction: `DELIMITER` scripts have never worked

Found by E4 failing, and it is not a Stage 3 bug — it is a Stage 0 one that
nothing had exercised.

`split.rs` treated a `DELIMITER` directive as a reason to **bail out**, returning
the whole buffer as one span with a comment explaining that the caller must not
rewrite it. That is half right: a routine body must reach the server whole. But
the span it returned still **contained the directive**, and `DELIMITER` is a
*client* directive — MySQL's server has never understood it. So the server got:

```
DELIMITER $$
CREATE PROCEDURE ...
```

and answered `You have an error in your SQL syntax ... near 'DELIMITER $$'`.

Every routine definition pasted into this app has failed since Stage 0, and the
error pointed at the user's SQL rather than at us. Nothing caught it because no
test ever ran a script containing a directive — the splitter tests asserted the
bail-out *shape* and stopped there, which is testing the implementation instead
of the behaviour.

**Fixed by honouring the directive rather than bailing out of it.** The splitter
now tracks the active terminator: a directive sets it, is consumed, and never
reaches a connection. `delimiter_detected` survives with a narrower job — it
still disables auto-LIMIT, which is correct for a script that defines routines.

This is strictly more capable than the old behaviour. `USE …; DROP …; DELIMITER
$$ CREATE …$$` now splits into three statements that run in order, which is what
made the E4 round trip possible at all — and hand-pasted routine definitions,
the ordinary way anyone creates a procedure, work for the first time.

Eight new splitter tests cover it: the directive never leaking into a statement,
custom terminators replacing rather than joining `;`, switching back to `;`
mid-script, multi-character terminators, `DELIMITERS` still being an identifier,
a bare `DELIMITER` setting nothing, and byte-exact offsets across a directive
with multibyte text.

#### Correction: there were two identifier quoters

Writing `sqlgen::quote_ident` turned up an existing `session::quote_ident`,
added in Stage 0 for `USE`. Two copies of identifier quoting is exactly the
split that bit us in Stage 1 with the statement splitter, so they are now one,
living in `sqlgen` where the rest of the generation is.

They also disagreed, and **the older one was right**. The new one stripped NUL;
the old one rejected it. Stripping produces a *different identifier* — `a\0b`
becomes `` `ab` ``, which may well name a real table that is not the one meant.
Refusing is the only answer that cannot be silently wrong. The fallible
signature won.

#### Correction: the seed was not re-runnable

`mise run db-up` re-seeds an existing container, and the seed dropped `users`
before `orders`, which holds the foreign key into it — so every re-run failed at
that line and left the fixture half-updated. Fixed by dropping `orders` first.
Worth noting because the *symptom* was a Stage 3 test failing on data that
looked like it should exist.

#### Detail worth keeping: `ordinal_position = 0` is not a parameter

For a function, `information_schema.parameters` returns the **return type** as
row 0, with a NULL name and NULL mode. Including it puts a nameless argument at
the front of every generated call. The query filters `ordinal_position > 0`, and
the live test asserts it explicitly rather than trusting the filter.

Functions also report a NULL `parameter_mode`; they are all `IN`, so that is
what we record rather than leaving a blank for the caller to interpret.

### Phase 2 — what shipped (2026-09-05)

Literal escaping, `generate_select` / `generate_drop` / `generate_call`, the
browse limit, and the command surface for all of it. **198 tests pass**
(139 unit + 3 fixture + 51 live + 5 keychain).

#### Correction: binary columns cannot be exported as INSERTs at all

The plan said blobs would become `0x…` hex literals. **They cannot**, and
finding out early is the only reason this stage will not ship corrupt exports.

`decode.rs` throws the bytes away:

```rust
Ok(b) => CellValue::Text(format!("<binary, {} bytes>", b.len())),
```

By the time a cell exists in a result set, a BLOB is the *string*
`<binary, 12 bytes>`. Any literal built from one writes that placeholder into
the column — silently, into a script that gets run somewhere else later. This is
precisely the failure the plan named as this stage's biggest risk, arriving from
a direction the plan did not anticipate: not a bug in the escaper, but missing
data upstream of it.

So `literal()` **refuses** binary rather than guessing, and says why. Phase 3
decides how export handles it — the re-run path can `SELECT HEX(col)` and get
real bytes, while the shown-rows path has nothing to work with and must say so.
The table in §3.3 has been overtaken by this: binary is not "emitted as `0x…`",
it is refused at this layer.

#### The escaper is verified against a real server, not against our beliefs

Unit tests for escaping assert what we *think* MySQL accepts, which is exactly
the kind of confidence that ships a corrupt export. So there is also a live test
that builds a literal for each of fifteen hostile strings, inserts it, reads it
back **as `HEX()`**, and requires the bytes to be identical:

`it's` · `back\slash` · `both ' and \` · `'; DROP TABLE users; --` · embedded
newline · carriage return · tab · Ctrl-Z · NUL · `héllo ★ 表 🔐` · double quotes ·
`% _` · trailing space · empty string

Reading back as hex matters: comparing decoded text would run the value through
the same decoder the rest of the app uses, and a shared bug would cancel out.

**One escaping assumption is recorded rather than solved.** The escaper targets
MySQL's default mode (`NO_BACKSLASH_ESCAPES` off). No single encoding is correct
in both modes — `''` is portable for the quote, but a literal backslash must be
doubled in the default mode and must *not* be under `NO_BACKSLASH_ESCAPES`. Hex
literals would be correct in both and unreadable in both, which defeats the
point of a script a human reviews.

#### Decisions worth keeping

- **A generated `DROP` has no `IF EXISTS`.** The object came from the schema
  tree, so it exists; `IF EXISTS` would turn a mistyped hand-edit into a silent
  no-op. Each one carries a one-line comment saying what it destroys, and
  `DROP DATABASE` says it takes every table, view and routine with it.
- **`CALL` snippets use `/* name type */` placeholders, not `NULL`s.** Filling
  in `NULL` would make the statement *runnable*, and a call that runs without
  being read is a call nobody decided to make. `OUT`/`INOUT` parameters become
  `@name` session variables, which is correct as written and needs no editing.
- **A function's snippet is a `SELECT`, not a `CALL`.**
- **The browse limit is a separate number from `MAX_ROWS`**, and a test asserts
  they are not equal — if they ever collapse into one, every double-click pulls
  five thousand rows. `app_defaults` hands both to the UI so neither is written
  down twice.
- **Auto-LIMIT leaves generated SELECTs alone**, verified live: they already
  carry an explicit `LIMIT`, and a second one is a syntax error.
- **Non-numeric text in a numeric column is refused, not quoted.** Unquoted
  output is spliced into the script, so `"1; DROP TABLE users"` arriving in a
  numeric column must stop rather than be emitted bare.
- **Non-finite floats are refused, not turned into NULL.** MySQL cannot store
  them, so reaching that branch means something is already wrong; silently
  writing NULL would change the data.

### Phase 3 — what shipped (2026-09-05)

CSV, `INSERT` scripts, the unbounded streaming re-run, and the clipboard text
builder. **219 tests pass** (154 unit + 3 fixture + 57 live + 5 keychain).

#### `CREATE TABLE` needed a second source, because the protocol has no lengths

The plan said `CREATE TABLE` would come from the result set's column metadata.
It can, but not well: **the MySQL protocol carries no length or precision.**
`type_info()` says `VARCHAR`, not `VARCHAR(190)` — and `VARCHAR` alone is a
syntax error. A derived schema also has no keys, no defaults and no nullability,
because none of that is on the wire either.

So there are two paths, and the caller says which applies:

| Rows came from | `CREATE TABLE` source | Fidelity |
|---|---|---|
| a real table (browse, or a plain `SELECT *`) | the server's `SHOW CREATE TABLE` | exact |
| anything else (a join, an expression) | derived + widened | approximate, and says so |

The derived schema widens (`VARCHAR` → `LONGTEXT`, `DECIMAL` → `DECIMAL(65,30)`,
any blob → `LONGBLOB`) and carries a four-line comment saying what it is. A
derived schema that *looks* like the original is worse than one that admits it
is not.

Both paths are proven by running them: E6 exports a real table, drops it,
replays the script and compares row-for-row — with a `BIGINT` past 2^53 and a
`DECIMAL(20,4)` in the data, which is exactly where a generator that trusts the
runtime type of a cell corrupts silently. A second live test runs a *derived*
schema against the server, because "does `VARCHAR` without a length parse" is
not a question to answer from memory.

#### The streaming path is the only thing in the app not capped by `MAX_ROWS`

`export_rerun` re-executes one statement and writes rows as they arrive, never
holding them all. The test that matters compares the two paths against the same
table: `big` has 7500 rows, `MAX_ROWS` is 5000, so the buffered path returns
5000 **and flags itself truncated** while the streaming path writes all 7500. If
those two ever agree, one of them is broken.

Three properties it had to have, each with a test:

- **Cancellable.** It runs on the tab's own exec connection under the same
  `running` flag as `run_script`, so the existing cancel button and `KILL QUERY`
  machinery apply unchanged. An export of ten million rows must be stoppable.
- **No half-written file wearing the real name.** Output goes to a `.part`
  sibling and is renamed only on success; a failure removes it. Not
  `files::write_atomic` — that takes a finished buffer, and the whole point here
  is that there isn't one — but the same guarantee.
- **The connection survives.** A stream abandoned mid-protocol is the classic
  way to poison a connection, so a test runs an export and then a query on the
  same tab.

#### Re-runnability refuses rather than guesses

The unbounded path re-executes a statement on its own, so offering it for the
wrong thing turns an "export" into a second `DELETE`. The rule is deliberately
narrow: **one statement, and it must return rows.** A multi-statement script may
have set up temp tables or moved the current database and will not reproduce
standalone; a `DELIMITER` block cannot be re-run at all. When we cannot promise
it, the option is not offered.

#### Decisions worth keeping

- **The grid is the source of truth for "what is shown".** Rows travel back to
  Rust to be exported rather than being re-read from the server, which costs one
  IPC hop over data that already made the trip and buys the only property that
  matters: the file matches what the user was looking at, column selection
  included.
- **CSV cannot express NULL.** `nullAs` decides which way the collapse goes, and
  when it is left empty *and* the data contains NULLs, the outcome carries a
  warning. Both directions are tested, including that an empty string must never
  become the word `NULL`.
- **The formula guard is opt-in.** A field starting `=` is executed by
  spreadsheets, and prefixing `'` defuses it — but that *changes the exported
  value*. A SQL client that quietly alters data is worse than one that warns.
- **The CSV round-trip test parses with an independently written reader**, so a
  shared misunderstanding of RFC 4180 cannot make it pass. It compares
  byte-exactly, including a CRLF *inside* a quoted field, which the format
  preserves and which my first assertion wrongly expected to be normalised.
- **Binary stops an `INSERT` export and only warns a CSV one.** CSV shows what
  the grid shows, placeholder included, which is consistent; an `INSERT` would
  write that placeholder *into the column*, so it refuses. The streaming path is
  the real answer, and the warning points at `HEX()`.
- **Streaming `INSERT`s are one statement per row**, deliberately unbatched:
  batching needs rows held back until a chunk is full, and holding nothing is
  the entire point of that path.
- **New dependency: `futures-util` 0.3** — `MIT OR Apache-2.0`, verified
  2026-09-05 from the vendored `Cargo.toml`. Already in the tree via sqlx, so
  nothing new is downloaded; it is the `.next()` on the row stream.

### Phase 4 — what shipped (2026-09-05)

Tree actions: double-click to browse, context menus on every node kind, and
routines in the tree at last. **223 tests pass** (158 unit + 3 fixture + 57 live
+ 5 keychain).

#### Behaviour change: clicking a table name no longer inserts it

Single-click on the label used to insert the table name at the cursor. That
cannot coexist with a double-click action on the same element — the first click
of every double-click would type into the editor.

Resolved by moving **Insert name at cursor** into the context menu, where it is
also easier to find than "click the text, but not the row". **Columns keep the
plain-click insert**: they have no double-click action, so nothing conflicts, and
it is the fastest way to build a select list while writing.

#### Single and double click are separated by deferral, not by luck

`clickOrDouble` defers the single action by 220ms and cancels it when a second
click arrives. The alternative — expanding immediately and opening a tab on the
double — makes the tree jump under the cursor mid-gesture.

The delay is invisible here because nothing in this tree is instant anyway:
expanding a table fetches its columns. Spending 220ms on something that was
already a round trip costs nothing; spending it on a keystroke would not have
been acceptable.

#### The tree is grouped, not just iconified

Tables and views were one flat list distinguished only by an emoji, and routines
were not there at all. Now each database expands into **Tables / Views /
Procedures / Functions**, counted, with empty groups omitted entirely. Tables
opens automatically, so the common case still costs no extra click.

Routines carry their signature inline — `(min_total, max_rows)` for a procedure,
`(uid) → int` for a function. A routine you cannot call without opening
something else is barely listed at all.

**A server that will not report routines does not break the tree.** Old versions
and restricted accounts exist, so `list_routines` failing degrades to an empty
group rather than taking the tables down with it.

#### The context menu is one implementation now

Moved out of `connections.ts` into `src/menu.ts`, where the schema tree can
reach it — the same move `choose()` made into `dialog.ts`, for the same reason.
It arrives with all three Stage 2 lessons intact: dismiss ignores events inside
the menu (without which every item is silently unclickable), Escape closes it,
and it is clamped to the viewport. It gained headings, so a menu says which
object it is acting on before offering to drop it.

#### Generated SQL opens in a new tab, never into the script in progress

The one exception is the routine append, which is what was asked for and what a
`CALL` is usually for — a step inside a script rather than a fresh task. Every
other action, `DROP` included, opens its own tab. Generating into the buffer
someone is working in would edit their work in order to show them something.

#### Wire-format tests, because Stage 2 earned them

Stage 2 shipped a bug where a field vanished between Rust and the UI and only a
test on the *serialised form* could have caught it. So `DropTarget`,
`RoutineKind`, `RoutineRef`, `ResultSet`, `CsvOptions`, `InsertOptions` and
`ExportFormat` each have a test that deserialises **the exact JSON `src/api.ts`
sends**. A rename on either side now fails in `cargo test` rather than at a
right-click.

One of them also pins something subtle: `CellValue` is untagged, so variant
order decides that `1` stays an `Int` rather than becoming a `Float`.

#### Still needs hands

E1, E2 and E3 are click-through milestones and remain unticked. The type checker
and the wire tests cover the shapes; they cannot tell whether a double-click
feels right or whether the groups read clearly.

### Phase 5 — what shipped (2026-09-05)

Column selection, clipboard copy, and the export dialog. **223 tests pass**;
build/clippy/fmt/tsc/vite clean.

#### The clipboard could not be verified empirically, and that is recorded

The plan said: check whether `navigator.clipboard` works in this webview before
designing around it. **It could not be checked.** A clipboard write requires a
user gesture, so a boot-time probe would fail even where a click-driven copy
succeeds — a false negative that would be worse than not testing.

What the configuration says is encouraging: `devUrl` is `http://localhost:1420`,
which is a secure context, and the bundled app is served from a scheme Tauri
registers as secure. But "should work" is exactly the reasoning that lost Stage 2
a whole delete feature to `window.confirm`.

So the requirement was met a different way: **`src/clipboard.ts` tries the modern
API, falls back to `document.execCommand('copy')` — which works in non-secure
contexts and older WebKit, precisely where the modern path fails — and throws if
both fail.** The caller reports the error in the results pane, and the message
says which path was used when it is the legacy one.

The real lesson from the delete button was never "test the clipboard"; it was
**never fail silently**. That is what is implemented, and it holds whichever
answer the click-through gives.

#### Column selection, and where it lives

Click selects, ctrl/cmd-click toggles, shift-click extends from the last click —
the three gestures a file list uses, because that is what people will try.
Clicking the only selected column clears it, so there is a way back to "nothing
selected" without hunting for one, and Escape clears everything.

Two details that only matter because the grid is virtualised:

- **The highlight is reapplied after every repaint.** Rows are recreated on
  scroll, so styling the cells once when the column was clicked would lose the
  selection the moment the grid moved.
- **The resize grip stops its own click.** It lives inside the header, so
  without that a drag also selects the column.

Selection lives on the `ScriptTab`, like widths and scroll position, so it
survives a tab switch. It is **cleared when the statement tab changes**: a
different statement has different columns, and indices from the old one would
highlight the wrong things.

#### Correction: column selection alone was not enough

The scope said "select specific columns and copy with or without headers", and
that is exactly what shipped first — and it was **missing the more common case**.
Reported straight away: *"what if I need a set of rows?"* There was no gesture
for it, because there was nothing in the grid to aim at.

Fixed by widening the model rather than bolting rows on beside columns.
Selection is now **two sets, intersected**, with one rule doing the work —
*empty means all*:

| rows | columns | selects |
|---|---|---|
| — | set | whole columns |
| set | — | whole rows |
| set | set | the block where they cross |
| — | — | the entire result |

Every case anyone wants falls out of that, and a single `applyGesture` handles
click / ctrl-click / shift-click for both sets, so the two cannot drift apart.
Clicking a cell selects one row and one column, so a cell *is* the intersection;
shift-clicking another extends both, which is how a block gets picked.

What the model cannot express is a ragged, non-rectangular selection. That is a
feature — a copy of one does not paste into anything.

**A row-number gutter was the missing affordance.** Rows could not be selected
partly because there was nothing to click; the gutter also makes dragging down a
range work, which is what people actually do instead of counting to the end and
shift-clicking. The corner cell selects everything, as a spreadsheet's does.

Three bugs this turned up while wiring it, all invisible to the Rust suite:

- **`table.rs th` made every `th` sticky to the top.** Correct for the header
  and wrong for a body row's gutter cell, which would have parked the row
  numbers over the header. The gutter now sticks only left; the corner sticks to
  both.
- **`tr:hover td` outranked `td.sel`.** More specific and later, so moving the
  pointer across a selection erased the highlight under it.
- **Ctrl+A cleared the sets.** Right for the data — empty means all — and wrong
  as feedback, since it answered "select everything" by highlighting nothing.
  It now fills both sets, and `isEverything()` keeps the two states equivalent
  wherever the difference would matter, such as whether the unbounded re-run is
  offered.

One knock-on worth stating: **`truncated` is only reported when every row is
being exported.** A hand-picked subset was never going to be "the query", so
warning that it is incomplete would be a warning about the wrong thing.

#### The export source is per tab, not global

An exported `CREATE TABLE` is exact when the rows came from a real table and a
widened approximation otherwise, so knowing which applies matters. That fact is
set **only by the schema tree's browse action** — the one place it is known for
certain — and stored on the tab it created. A module-level global would have gone
stale on the first tab switch and made an export claim a fidelity it did not
have.

Nothing tries to infer it by parsing the SQL. That would be wrong for a join.

#### The unbounded re-run is disabled with a reason, not hidden

The "re-run the query" scope is greyed out, with the option text saying why, when
the statement cannot be re-run standalone or when a column selection is active
(the re-run returns the query's own columns, not a subset). Disabling with a
reason beats offering it and being wrong once — and beats hiding it, which
leaves the user wondering where it went.

When a result is truncated, the dialog **pre-selects** the re-run, since that is
almost always what was wanted.

#### Truncation is stated in words, every time

`describeExport` says the row count, the size and the path, and when the source
was truncated it says outright that the query has more rows and how to get them.
Writing 5000 rows and letting it look like the whole table is the same
silent-wrong-answer failure as Stage 0's empty schema tree.

A cancelled save dialog returns `null` and is **not** reported as a failure; a
refusal keeps the dialog open with its values so it can be corrected rather than
re-entered.

#### Still needs hands

E5, E7 and E8 are click-through milestones. The app could not be booted for a
smoke test — port 1420 was already in use by the running instance — so **the dev
app should be restarted** to pick up both the frontend and the new Rust
commands.

The clipboard is the one thing to try first: Copy should either work or say why,
and the message will name the legacy path if that is what carried it.

## 7. Risks / things to watch

- **The `INSERT` generator is the one place a bug corrupts user data.** Everything
  else in this stage produces text a human reviews. An exported script is often
  run somewhere else, later, unreviewed. It gets the most tests.
- **`DROP` generation is one careless default away from being dangerous.** No
  menu item runs anything; no `DROP` is pre-selected; the generated statement
  lands in the editor and stops.
- **Double-click on a tree that already handles single-click.** Single-click
  expands a table and inserts a column name. Adding double-click means the
  single-click handler must not fire destructively first — needs a real
  interaction pass, not a `dblclick` listener bolted on.
- **Streaming export and the tab's exec connection.** An unbounded re-run holds a
  connection for a long time. It must not block the tab, and cancelling it must
  work — the Stage 0 `KILL QUERY` machinery already exists and should be reused
  rather than reinvented.
- **`SHOW CREATE` privileges.** Common in shared environments. Degrade well.
