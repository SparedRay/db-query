## 1. Scope

### In scope
- **Ad-hoc connections** — today's Connect button, unchanged in spirit: connect
  without saving anything
- **Saved connection profiles** — name, colour, host, port, user, default
  database; persisted across restarts
- **Passwords in the OS keychain**, opt-in per connection, never in the config file
- **A connection rail** down the left: one icon per connection, click to switch,
  `+` to add
- **Several connections live at once.** Switching is a UI focus change, not a
  disconnect
- **Tabs are per connection.** Switching restores that connection's tabs,
  results and editor state
- Per-connection schema tree and active database
- Edit / duplicate / delete a profile; delete removes its keychain secret too

### Explicitly out of scope
- Restoring tabs across an app restart (decided 2026-09-05 — this session only)
- Storing unsaved buffer contents anywhere
- Confirm-on-destructive-SQL for production connections (decided 2026-09-05 —
  colour and label only; see Backlog)
- SSH tunnels, socket files, read replicas, connection pooling knobs
- Import/export of connection profiles, or syncing them anywhere
- Engines other than MySQL (still Stage 0's boundary)

> Same rule as before: anything not on the in-scope list goes to the backlog.

## 2. Architecture decisions

| Decision | Choice | Why |
|---|---|---|
| Live connections | **Many at once**, one per opened connection | "Switching restores your tabs" is only true if the sessions survive. Disconnecting would kill running queries and lose `USE`, temp tables and variables |
| Switching | **A frontend concern only** | The backend gets no notion of an "active" connection — every command names the connection or tab it acts on. A hidden active pointer is exactly what makes "it ran on the wrong server" bugs possible |
| Connection budget | **(N tabs + 2) per connection** | Stage 1's model, now multiplied. Lazy tab connections keep the floor at 2 per connection |
| Profile storage | Plain JSON in the app config dir, `0600` on Unix, **versioned from day one** | Non-secret by construction, human-inspectable, and a version field costs nothing now versus a migration guess later |
| Password storage | **OS keychain via `keyring` 4.x (`v1` feature)**, opt-in per profile | Decided 2026-09-05. Maps to Windows Credential Manager / macOS Keychain / Linux Secret Service. The config file never contains a secret, so it can be read, diffed or synced without leaking one |
| keyring major version | **4.x, not 3.x** | 3.x put platform backends behind opt-in features and fell back to a **mock store that silently does nothing** — "saved" passwords that never persist. 4.x enables all three natively by default. Worth more than 3.x's extra maturity |
| Store verification | **Read the secret back immediately after writing it** | The failure that matters is silently not storing. A read-back turns it into a visible error on every platform, and costs nothing |
| No keychain available | **Degrade, never fail** | A headless or locked-down box has no Secret Service. The profile still saves; it just prompts for the password on connect |
| Password in memory | Held for the connection's life, `zeroize`d on drop | Unavoidable: lazy per-tab connections must be able to authenticate later. Zeroizing is hygiene, not a guarantee — see §6 |
| Tab ↔ connection binding | `TabSession` holds an `Arc<ServerConn>` | Commands stay `tab_id`-only, and a tab physically cannot run against the wrong server |
| Tab memory | **Session only** | Decided 2026-09-05. Delivers the described behaviour with no on-disk format to design or migrate |
| Connection identity | User-chosen **name + colour** | Answers "which server am I on" at a glance, which is the cheapest half of environment safety |
| Config writes | Reuse `files::write_atomic` | Already built and tested in Stage 1; a half-written connections file would be worse than none |

### State shape

```rust
pub type ConnectionId = String;   // stable; also the keychain account name

pub struct AppState {
    /// Every live connection. Keyed by id; the frontend decides which is shown.
    connections: Mutex<HashMap<ConnectionId, Arc<ServerConn>>>,
    /// Flat, because a tab already knows its server.
    tabs: Mutex<HashMap<TabId, Arc<TabSession>>>,
}

pub struct ServerConn {
    id: ConnectionId,
    profile: ConnProfile,          // name, colour, host, port, user, database
    password: Secret,              // zeroized on drop
    killer: Mutex<MySqlConnection>,
    meta: Mutex<MySqlConnection>,
    schema_cache: Mutex<HashMap<String, DbSchema>>,
    server_version: String,
    introspection_count: AtomicU64,
}

pub struct TabSession {
    server: Arc<ServerConn>,       // binds the tab to one connection, permanently
    exec: Mutex<Option<MySqlConnection>>,
    conn_id: AtomicU64,
    current_db: Mutex<Option<String>>,
    running: AtomicBool,
    cancel_requested: AtomicBool,
}
```

**Stage 1's lock discipline carries over unchanged, plus one addition:**

1. Never hold the `connections` or `tabs` map lock across an `await` — clone the
   `Arc` out and drop the guard.
2. `cancel_query` touches only its connection's `killer` and the tab's `conn_id`.
3. The killer connection does nothing but `KILL QUERY`.
4. Lock order: `tabs` → `TabSession.exec` → `ServerConn.*`.
5. **New:** `disconnect(connection_id)` must close that connection's tab
   connections too, and only that connection's. Tabs are found by comparing
   `Arc::ptr_eq` on their `server`, never by a stale copy of the id.

### Platform support — verified 2026-09-05, not assumed

`keyring` 4.x with default features (`v1`) selects the native store per target:

| Platform | Credential store | Backend crate | Target gate |
|---|---|---|---|
| **Windows** | **Windows Credential Manager** | `windows-native-keyring-store` 1.1.0 | `cfg(target_os = "windows")` |
| macOS / iOS | Keychain Services | `apple-native-keyring-store` 1.0.2 | `cfg(any(macos, ios))` |
| Linux / *nix | Secret Service (D-Bus) | `zbus-secret-service-keyring-store` 1.0.1 | `cfg(all(unix, not(apple/android)))` |

**Evidence, not assumption:**

- `cargo check --target x86_64-pc-windows-msvc` compiles the full keyring
  surface from a Linux host and resolves `windows-native-keyring-store` +
  `windows-sys`, proving the Windows backend is real and the target gating is
  right.
  **Correction (2026-09-05):** that check works on a *standalone crate whose
  only dependency is `keyring`*. It does **not** work on this application —
  `ring`, rustls's crypto backend, runs a build script that needs a C compiler
  for the Windows target, which a plain Linux host does not have. Cross-checking
  the whole app would need `mingw-w64` and the `x86_64-pc-windows-gnu` target.
  So the honest position is: **the app is verified on Windows by building it on
  Windows**, and the cross-check is a cheap smoke test of the keyring surface
  only.
- A store → read-back → delete round trip runs green on Linux against a live
  `gnome-keyring`.
- Linux uses `zbus` (pure Rust D-Bus), not `libdbus`, so **no new C library is
  linked** on any platform.

**Still unverified: the Windows path at runtime.** Compiling is not running.
Credential Manager behaviour needs one real check on a Windows machine — that
is milestone C3, not an assumption to carry.

### Supersedes Stage 0

Stage 0's `ConnConfig` documented "password: in memory only — v1 does not
persist credentials". That stance changes here: passwords may be persisted, in
the OS keychain, only when the user opts in per connection. The config file
still never holds one.

```rust
struct ConnProfile {
    id: ConnectionId,
    name: String,             // "prod-eu", "local"
    colour: String,           // "#3b82f6" — identification, not decoration
    host: String,
    port: u16,
    user: String,
    database: Option<String>,
    allow_invalid_certs: bool,
    /// True when a secret exists in the keychain for this id. Derived, never

}

struct ConnectionStatus {
    id: ConnectionId,
    name: String,
    colour: String,
```

### Phase 1 — what shipped

Backend is fully multi-connection. Six new live tests:

| Test | Proves |
|---|---|
| `two_connections_keep_separate_sessions` | **C4.** `SELECT DATABASE()` differs per connection — the server agrees, not just our bookkeeping |
| `a_slow_query_on_one_connection_does_not_block_another` | **C5.** Stage 1 proved this across tabs; this proves it across servers |
| `disconnecting_one_connection_leaves_the_other_working` | Closing one takes its tabs with it and leaves the other's tabs, sessions and cache untouched |
| `schema_caches_are_per_connection` | Warming one cache does not make another look warm — which would silently disable the other's lint checks |
| `list_connections_reports_live_state_and_tab_counts` | The counts the rail will render are real |
| `cancel_does_not_reach_across_connections` | Cancel stays inside its own connection |

**Decisions and corrections during implementation:**

- **Tabs no longer auto-create.** Stage 1 auto-created a tab on first use to
  dodge an ordering race. That is no longer possible: a tab needs a connection,
  and *guessing* which one is precisely the ambient-state mistake this stage
  exists to prevent. `open_tab(connection_id, tab_id)` is now required, and an
  unattached tab gets a clear error instead of a wrong server.
- **`TabStatus.connected` changed meaning**, from "the app has a connection" to
  "this tab has a live session". That is the only sense that survives multiple
  connections. A test was updated to assert both halves — that an unattached tab
  reports no session, and that attaching one still opens no *server* connection
  until something runs.
- **`lint_sql` resolves the schema through the tab, not a caller-supplied
  connection id.** The tab is the one source that cannot name the wrong server.
- **`ConnProfile` carries no password.** It is the exact shape Phase 2 will
  persist, so the config file is secret-free by construction rather than by
  remembering to strip a field.

### Phase 2 — what shipped

`secrets.rs` (Secret newtype + keychain) and `profiles.rs` (versioned config
file). 12 new unit tests, 5 keychain round-trip tests, 5 leakage audits.

**The security claims, each with the test that checks it:**

| Claim | Test |
|---|---|
| The config file cannot contain a password | `the_file_contains_no_secret` — and structurally, since `ConnProfile` has no such field |
| The file is owner-only, and stays so after a rewrite | `the_file_is_owner_only` (rewrite included, because `write_atomic` renames over it) |
| A corrupt file is preserved, not deleted, and the app still opens | `a_corrupt_file_is_moved_aside_not_deleted` |
| `Debug` cannot leak a secret, even nested in another struct | `debug_never_prints_the_secret` |
| A wrong password never appears in a connection error | `a_failed_connection_never_echoes_the_password` |
| Nor in an IO error, a TLS refusal, or a query error | three more leakage audits |
| A stored secret really is deleted with its profile | `store_load_delete_round_trip` |
| Awkward passwords survive the keychain intact | `secrets_with_awkward_bytes_survive` |

**Decisions made while implementing:**

- **`password` on `save_profile` is a three-way instruction, not a value:**
  a string means remember it, `""` means forget it, `None` means leave what is
  stored alone. Without the third case, editing a profile's port would silently
  wipe its password.
- **`remember_password` is `#[serde(skip)]`.** It is derived from the keychain
  on every read, never written. A profile file copied to another machine then
  reports the truth *there*, instead of claiming a password that does not exist.
- **Permissions are applied before content.** The file is created and chmod'd
  `0600` first, then written — and re-chmod'd after, because `write_atomic`
  renames a fresh file over the target and a new file does not inherit the old
  one's mode. The test covers the rewrite case for exactly that reason.
- **A corrupt config is moved aside, not deleted or refused.** Refusing to start
  is the one failure that would make the app unopenable; deleting would lose a
  list of servers silently. Renaming to `connections.json.corrupt-<ts>` does
  neither.
- **`load` treats "no credential store" as "nothing stored".** From the caller's
  point of view they are the same situation and lead to the same action —
  prompt.

### Bugs found during the C1-C5 click-through (2026-09-05)

Four, all frontend, none reachable by the backend suite. Three were found by
reading the dev server's runtime log rather than by any test — worth keeping in
the loop for a stage with this much UI.

**1. Failed connection attempts left dead icons in the rail, and put their error
in the wrong place.** The submit handler added the entry *before* connecting,
and `ConnectionManager.connect` swallowed the error into `notify()` — which
writes to the results pane, not to the dialog the user is looking at. So every
typo produced an icon to clean up and an error nowhere near the field that
caused it.

Fixed by changing the shape rather than patching it: `attempt()` returns the
error instead of displaying it, so the caller decides where it belongs — the
rail wants the results pane, the dialog wants its own error line. And the entry
only joins the rail once a connection actually succeeds.

That also allowed a better ordering: **connect first, persist only on success**.
A profile is now written down only once it is known to work, and the password
reaches the keychain only after the server has accepted it. (Trade-off worth
naming: you can no longer save a profile for a server that is currently down.
Backlogged.)

**2. Every context-menu item was silently unclickable.** The menu dismissed on
`mousedown` anywhere, which tore it down before the button's `click` — which
fires on mouseup — could land. The dismiss handler now ignores events inside the
menu. Escape closes it too, and it is clamped to the viewport.

**3. Deleting a connection silently did nothing.** `window.confirm` is
intercepted by Tauri and routed to the dialog plugin, which needs
`dialog:allow-confirm` — we had granted only `dialog:default`. The call rejected
with `dialog.confirm not allowed`, so the promise never resolved and `remove()`
never ran. No visible failure at all; only the console said anything.

Fixed by *not* using native dialogs: `choose()` moved out of `files.ts` into
`src/dialog.ts` and is now shared. It needs no permission, matches the rest of
the UI, and can offer more than two answers — the delete prompt now spells out
that the keychain entry goes too, and that connected tabs will close.

The general rule this earns: **`window.confirm` / `alert` / `prompt` are not
available to us.** Anything that asks the user a question goes through
`src/dialog.ts`.

**4. A tab could be created with no connection.** Three call sites, not one: the
boot path, the tab bar's `+`, and `Ctrl+O`. Only the first was obvious; the other
two are reachable states the type checker cannot see, and surfaced as a runtime
throw in the dev log.

### Bug: remembered passwords looked forgotten after every restart (2026-09-05)

**Reported as:** "it's storing the connection but is not really storing the
password, every time I have to put it again."

The password *was* stored. Probing the machine's keychain directly for the two
saved profile ids returned `has_stored=true` for both, and gnome-keyring was
running with its `secrets` component. Nothing about the write path was broken.

**Cause: one struct serving two wire formats with opposite requirements.**
`ConnProfile` carried `remember_password` behind `#[serde(skip)]`. That is
correct for the config file — a profile copied to another machine must not claim
a password that machine does not have — and `skip` is `skip_serializing` *and*
`skip_deserializing`. The same struct is also the IPC response, so
`list_profiles` computed the flag from the keychain and serde dropped it on the
way out. The frontend saw `undefined`, concluded nothing was stored, and opened
the editor to prompt.

The comment above the field documented the config-file reasoning, correctly. The
frontend was simply not considered a second consumer of the same derive.

Two things hid it. Within a session it looked fine, because `save_profile`
returns `passwordStored` as a *separate* field and the frontend assigns it to
the in-memory entry — so the flag was right until the next launch, and the
symptom only appeared at boot. And nothing failed: no error, no log, a
successful save and a successful store. The wrong value was a missing key.

**Fix: the derived fact moved to a type that only exists on the wire.**
`ProfileView` is `ConnProfile` flattened plus `remember_password`, and
`ConnProfile` no longer has the field at all — so the disk shape is what gets
written to disk, and the mistake is no longer expressible. `profiles::LoadOutcome`
lost its `Serialize` for the same reason: it is what came off disk, not what the
UI receives. The TypeScript side mirrors the split (`ConnProfile` +
`ProfileView`), and `tsc` immediately found the one place that had been building
a profile with a derived field on it.

**Tests: four, all on the wire format**, because that is the only place the bug
was visible — `rememberPassword` is present and true when a secret exists, false
when not, the flattened object is flat and camelCased, and a `ConnProfile` round
trip cannot invent the field. A test that had only exercised the Rust values
would have passed throughout.

**The general lesson, worth carrying forward:** a `#[serde(...)]` attribute is a
property of a *format*, not of a type. Any struct that is both persisted and
sent over IPC has two formats and needs two types. Worth auditing the rest of
the command surface for the same shape.

### Phases 3-4 — what shipped

`src/connections.ts` owns the rail, the context menu and connection lifecycle;
`tabs.ts` gained per-connection workspaces.

**Decisions and corrections during implementation:**

- **`ScriptTab.connectionId` collided with an existing field.** Stage 1's
  `connectionId` was *MySQL's own* connection id for the tab. It is now
  `serverConnId`, which is what it always meant — the clash forced a name that
  was clearer anyway.
- **A tab cannot exist without a connection**, so nothing creates one at boot.
  Three call sites needed guarding rather than one: the boot path, the tab
  bar's `+` (now absent instead of present-and-throwing), and `Ctrl+O`, which
  otherwise threw when a file was opened before connecting. The runtime error in
  the dev log is what surfaced the last two — the type checker cannot see them.
- **Untitled numbering is per connection.** Each workspace counts from
  `Untitled-1`, which is what a workspace means.
- **Each connection keeps its own schema-tree element**, swapped in and out
  rather than rebuilt. Rebuilding would have collapsed everything the user had
  expanded on every switch, and the Rust cache would have hidden the cost.
- **`hostLabel` disappeared.** It was a single-connection global; the status bar
  now derives its text from the active connection, so there is one source rather
  than a copy that could drift.
- **The connection-count tooltip is now cross-connection**, listing each live
  connection's arithmetic and the total. With `(tabs + 2) × connections` it is
  the number a DBA would actually ask about.
- **An ad-hoc connection is marked in the rail** with a dot, so "why is this gone
  tomorrow" has a visible answer before it happens rather than after.
- **The tab strip carries the active connection's colour** (added on request):
  the selected tab's accent, the busy spinner and the unsaved dot all use it.
  Only one connection's tabs are visible at a time, so without it the strip
  looks identical whichever server you are on — which is exactly the moment you
  want to be certain.

| `sample_files` | 3 | Stage 1 encoding fixtures (UTF-8, CRLF, Latin-1) |
| `live_mysql` (`--ignored`) | 41 | Stage 0 `m1`-`m5`, Stage 1 `n5`, Stage 2 multi-connection |
| `keychain` (`--ignored`) | 5 | Secret Service round trip, overwrite, delete, awkward bytes |

**C6 was checked by name, not by count** — that is the whole point of the
milestone. Stage 0's `m1_*`, `m2_*`, `m2b_*`, `m3_*` and `m5_*` and Stage 1's
`n5_*` and `files::*` are all present and passing, so nothing was quietly
dropped to make the numbers work.

**C2 was checked against the real config file**, not a fixture. The live
`connections.json` for two saved connections contains `id`, `name`, `colour`,
`host`, `port`, `user`, `database` and `allowInvalidCerts` — and nothing else.
No password, and no field that could hold one.

**C3 was checked against the real keychain.** Both saved profile ids returned
`has_stored=true` from the machine's Secret Service, and the IPC payload
`list_profiles` now produces was serialised and inspected directly. This is what
caught the remembered-password bug above: the secret was there the whole time,
and the round trip through the *wire format* was the only place it showed.

#### Connection arithmetic — measured, not estimated

Two connections open eagerly per server (`meta` for `information_schema`,
`killer` for `KILL QUERY`), and one per tab, opened lazily on first run and
released on close.

| Scenario | Sockets |
|---|---|
| Per connection, idle | 2 |
| Per tab, once it has run something | 1 |
| **3 connections × 3 tabs, nothing run yet** | **6** |
| **3 connections × 3 tabs, all active** | **15** |

Against the fixture's `max_connections = 151` (`max_user_connections = 0`,
unlimited), 15 is **10% of the server's budget**. Room for roughly 30
connections at three tabs each before the server, not the app, becomes the
limit — well beyond what this UI is for.

The cost worth noting is that it is **2 per connection before a single query
runs**. That is the price of cancellation working at all: `KILL QUERY` cannot be
sent down the connection it is trying to kill, and introspection sharing the
tab's connection would have meant schema loads fighting with the user's query.
Both were deliberate; both are re-examinable if connection count ever bites.

`wait_timeout` on the server is 28800s (8 hours), which is exactly the case
`ensure_exec` exists for — a tab left open overnight finds its connection reaped
and transparently reopens it.

### Carried forward into Stage 3

- **C3w — Windows on real hardware. Not done.** The keychain backend is
  cross-checked to `x86_64-pc-windows-msvc` as a standalone crate, which proves
  the target gating compiles and nothing more. The full app cannot be
  cross-checked (`ring` needs a Windows C toolchain — see §2), so *nothing here
  has ever been run on Windows*. Since that is the primary dev machine, this is
  the first thing the next stage should do: `cargo test`, the keychain round
  trip, and confirmation that the entry appears in **Control Panel → Credential
  Manager → Windows Credentials** and disappears when the connection is deleted.
- **No frontend test layer.** Five of the bugs in this stage were frontend-only
  and invisible to the Rust suite; three were found by reading the dev server's
  runtime log rather than by any test at all. The remembered-password bug was
  the exception that proves the point — it was a *wire format* bug, catchable
  from Rust, and only once someone thought to assert on the serialised JSON.
- **Saving a profile for a server that is currently down.** Connect-first means
  a profile is only written once it works. Correct default, occasionally wrong.

## 6. Risks / things to watch

- **A secret leaking into somewhere ordinary.** Config files, log lines, error
  strings, a `Debug` derive, a panic message, a connection URL in a TLS error.
  This is the risk that matters most, because it is silent and permanent once
  the file is in a backup. The `Secret` newtype with a redacting `Debug`, plus
  an explicit audit of every error path, is the mitigation — not vigilance.
- **`zeroize` is hygiene, not a guarantee.** A `String` that reallocates leaves
  copies behind that nothing can reach to clear, and the OS may have paged the
  password to swap already. Worth doing; not worth believing in. Say so, rather
  than implying the password is unrecoverable from memory.
- **Orphaned keychain entries.** Delete a profile without deleting its secret and
  the password outlives the thing that explained what it was for. Deletion must
  cover both, and a failure to remove the secret must be surfaced, not swallowed.
- **The connection budget multiplies.** Stage 1 was `N + 2`; this is
  `(N + 2) × connections`. Three connections with three tabs each is 15
  connections against possibly the same server, where `max_connections`
  commonly defaults to 151. Lazy tab connections keep idle connections at 2 per
  connection, but the number should be visible.
- **"Active connection" must not leak into the backend.** Every command names
  its target. The moment the backend holds an active pointer, a switch racing an
  in-flight query can run it against the wrong server — the worst bug this
  project could ship.
- **Switching connections mid-query.** Stage 1 taught this the hard way: anything
  the user can switch away from and back to must be *state on the thing they
  switched away from*. That now applies one level up — a connection's running
  queries, tab set and schema must all survive being switched away from.
- **No keychain on the machine.** A headless CI box, a minimal WM, a locked-down
  work laptop. Saving must not fail and connecting must not silently do nothing;
  it prompts, and the UI explains why once rather than nagging.
- **A keychain that accepts writes and stores nothing.** The worst version of the
  above, because it looks like success. This is precisely why `keyring` 3.x was
  rejected — its default was a mock store — and why every write is read back
  before we claim the password was saved.
- **The Windows path can barely be exercised from the Linux dev machine.** Even
  compiling is limited: `ring` needs a Windows C toolchain, so only a
  keyring-only crate cross-checks, not the app. Cross-checking catches backend
  and gating rot; it cannot catch a Credential Manager behaviour difference and
  it cannot check the app builds. **Anything touching secrets needs a real pass
  on Windows before this stage is frozen** — and so does at least one full
  `cargo build` there.
- **Config file corruption.** A truncated `connections.json` must produce a
  readable error and an empty list, never a panic on launch — the one failure
  mode that would make the app unopenable.

## 7. Notes for the implementing agent

**Build order.** Phase 1 before 4; Phase 2 is independent of Phase 1 and can
land in parallel. Phase 3 needs both.

```
src-tauri/src/
  session.rs     ServerConn keyed by id, TabSession bound to a connection
  profiles.rs    ConnProfile, connections.json (versioned, atomic, 0600)
  secrets.rs     keyring wrapper, Secret newtype, degradation policy
src/
  connections.ts rail, editor dialog, per-connection workspace switching
  tabs.ts        ScriptTab gains connectionId; render filtered by connection
```

**Ground rules** (Stage 0 and Stage 1's still apply, plus)
- No command returns a password, ever — not even the one just saved.
- `Secret` never derives `Debug`, `Serialize` or `Display`. It gets a hand-written
  `Debug` that prints `<redacted>` and nothing else.
- The config file is written atomically and chmod `0600` before anything is
  written into it, not after.
- Every command names the connection or tab it acts on. There is no ambient
  "current" connection in Rust.
- **No `window.confirm` / `alert` / `prompt`.** Tauri routes them through the
  dialog plugin, where a missing permission makes them reject silently and the
  caller do nothing. Ask through `src/dialog.ts` instead.

**Licensing.** New dependencies to verify and record before use — all
permissive as of 2026-09-05:

| Dependency | License |
|---|---|
| `keyring` 4.2.0 | MIT OR Apache-2.0 |
| `keyring-core` 1.0.0 | MIT OR Apache-2.0 |
| `windows-native-keyring-store` 1.1.0 | MIT OR Apache-2.0 |
| `apple-native-keyring-store` 1.0.2 | MIT OR Apache-2.0 |
| `zbus-secret-service-keyring-store` 1.0.1 | MIT OR Apache-2.0 |
| `zeroize` 1.9.0 | Apache-2.0 OR MIT |

On Linux `keyring` talks to `org.freedesktop.secrets` over D-Bus via `zbus`
(pure Rust) — a system service, not a bundled library, so **no new C dependency
is linked on any platform**. On Windows it calls the OS credential API through
`windows-sys`; on macOS, Security.framework. Stage 0's three standing rules still
bind: no `libmysqlclient`, no GPL client source consulted, WebKitGTK and
lightningcss remain the only non-permissive pieces.
