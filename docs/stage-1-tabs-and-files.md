## 1. Scope

### In scope
- Multiple script tabs; each keeps its own text, cursor, undo history
- Each tab owns its result area — statement tabs, grid, status bar
- Open `.sql` files into a new tab, via dialog and via drag-and-drop
- Save (`Ctrl+S`) and Save As; dirty indicator; confirm before losing edits
- An extensible file-type registry, so a future engine registers its own
  extensions instead of us hard-coding them
- **Tabs run concurrently** — one connection per tab, created lazily
- Per-tab cancel, per-tab active database, per-tab busy state

### Explicitly out of scope
- Restoring tabs across app restarts (see Backlog — decided 2026-09-05)
- Connecting to more than one *server* at a time (still one server per window;
  what changes is that we now hold several connections *to it*)
- Split/side-by-side editor panes
- Tab groups, pinning, reordering by drag
- A file tree / project browser
- Export of results (still Stage 0 backlog)

## 2. Architecture decisions

| Decision | Choice | Why |
|---|---|---|
| Concurrency | **One exec connection per tab**, created lazily on first run | Tabs that queue behind each other are not tabs. A slow query in one must not stall the rest — that is the freeze this project exists to avoid |
| Connection budget | **N + 2**: one exec per tab, one shared *killer*, one shared *meta* | See below. Idle tabs cost nothing |
| Killer connection | Shared across tabs, **only ever issues `KILL QUERY`** | Cancellation is the flagship feature; nothing may be able to block it |
| Meta connection | Separate connection for `information_schema` | Introspection must not block on a running query, nor contend with cancel. Stage 0 already flags `information_schema` as slow on large servers |
| Schema cache | **Shared** across tabs, keyed by database | Schema is a property of the server, not of a tab |
| Active database | **Per tab** | Each script gets its own `USE`. Matches how a script behaves when run standalone |
| Tab identity | `TabId` minted by the frontend, opaque to Rust | Frontend owns tab lifecycle; Rust just maps id → session |
| Editor state | One `EditorView`, swap `EditorState` per tab | Idiomatic CodeMirror 6, preserves per-tab undo history, avoids N live editors |
| File types | Runtime **registry** (`supported_file_types`) | The "future integrations" hook: a Postgres driver registers `.pgsql` and the dialog filter follows, rather than a hard-coded list |
| Non-UTF-8 files | Open lossily, **but disable Save** until Save As | Saving a lossily-decoded buffer would silently corrupt the user's file |
| Line endings | Detect dominant ending on open, preserve on save | Otherwise every save rewrites the whole file as a diff |
| Large files | Warn > 2 MB, refuse > 25 MB | A dump loaded into CodeMirror freezes the UI. Refusing is honest; freezing is not |
| Tab persistence | **Not now** | Decided 2026-09-05. Needs a versioned workspace file and stale-path recovery; out of this stage |

### Why N + 2, and the lock discipline that makes it safe

Stage 0 shipped a bug where a single mutex around both connections made
`cancel_query` deadlock against the very query it existed to kill. The same
trap scales up here, so the rule is explicit:

```rust
pub struct AppState {
    /// Server identity + shared connections. One server per window.
    conn: Mutex<Option<ServerConn>>,
    /// Per-tab sessions. The map lock is NEVER held across an await.
    tabs: Mutex<HashMap<TabId, Arc<TabSession>>>,
}

pub struct ServerConn {
    config: ConnConfig,                        // needed to open new tab connections
    killer: Mutex<MySqlConnection>,            // KILL QUERY only
    meta: Mutex<MySqlConnection>,              // information_schema only
    schema_cache: Mutex<HashMap<String, DbSchema>>,
    host_label: String,
    server_version: String,
}

pub struct TabSession {
    exec: Mutex<Option<MySqlConnection>>,      // None until the tab first runs
    conn_id: AtomicU64,                        // SELECT CONNECTION_ID() on `exec`
    current_db: Mutex<Option<String>>,
    running: AtomicBool,
    cancel_requested: AtomicBool,
}
```

**Rules, in order of how badly they bite:**

1. **Never hold the `tabs` map lock across an `await`.** Clone the
   `Arc<TabSession>` out, drop the guard, then do the work. Holding it would
   serialize every tab through one mutex and reintroduce exactly the stall we
   are removing.
2. **`cancel_query` touches only `killer` + the tab's `conn_id`.** It must
   never take that tab's `exec` lock, which the running query holds.
3. **The killer connection does nothing else.** Not introspection, not
   `SELECT 1`. If it can be busy, cancel can be blocked.
4. **Lock order, where two are needed: `tabs` → `TabSession.exec` → `conn`.**
   Never the reverse.

## 3. Backend command surface

Commands that touch a tab take a `tabId`. Stateless helpers do not.

```rust
// --- connection (unchanged shape, new internals)
connect(config: ConnConfig)   -> Result<ConnInfo>   // opens killer + meta only
disconnect()                  -> Result<()>         // closes every tab connection too

// --- tab lifecycle
open_tab(tab_id: TabId)       -> Result<()>         // register; NO connection yet
close_tab(tab_id: TabId)      -> Result<()>         // close its connection, drop state

// --- per tab
use_database(tab_id, db)      -> Result<()>
tab_status(tab_id)            -> Result<TabStatus>  // current db, running, connected
run_script(tab_id, sql, auto_limit, timeout_secs) -> Result<ScriptResult>
cancel_query(tab_id)          -> Result<()>
lint_sql(tab_id, sql)         -> Result<Vec<Diagnostic>>   // needs the tab's current db

// --- shared (meta connection + shared cache)
list_tables(db)               -> Result<Vec<TableRef>>
list_columns(db, table)       -> Result<Vec<ColumnInfo>>
refresh_schema(db)            -> Result<()>

// --- stateless, unchanged
split_sql(sql)                -> Result<SplitOutput>
statement_at_cursor(sql, cursor) -> Result<Option<String>>

// --- files (new)
supported_file_types()        -> Result<Vec<FileTypeSpec>>
open_file_dialog()            -> Result<Option<OpenedFile>>   // pick + read, one round trip
read_file(path)               -> Result<OpenedFile>           // drag-drop, recent files
save_file(path, contents, expect_mtime) -> Result<SaveOutcome>
save_file_dialog(suggested_name, contents) -> Result<Option<String>>
```

```rust
struct TabStatus {
    connected: bool,
    running: bool,
    current_database: Option<String>,
}

struct FileTypeSpec {
    label: String,            // "SQL"
    extensions: Vec<String>,  // ["sql", "ddl", "dml"]
    dialect: String,          // "mysql" — drives the CodeMirror dialect
}

struct OpenedFile {
    path: String,
    name: String,
    contents: String,
    size_bytes: u64,
    dialect: String,
    /// "utf-8" | "utf-8-lossy". Lossy means Save must be disabled.
    encoding: String,
    /// "lf" | "crlf" — preserved on save.
    line_ending: String,
    mtime_ms: u64,
}

enum SaveOutcome {
    Saved { mtime_ms: u64 },
    /// The file changed on disk since we opened it — do not clobber silently.
    Conflict { disk_mtime_ms: u64 },
}
```

## 5b. Phase 1 — what shipped, and what it taught us

Backend is fully per-tab. Verified by 7 new live tests:

| Test | Proves |
|---|---|
| `n5_a_slow_query_in_one_tab_does_not_block_another` | **N5.** A 5s query in one tab; another returns in <2s |
| `cancel_targets_only_the_requesting_tab` | Cancelling A leaves B's query running and uncancelled |
| `tab_connections_are_lazy_and_released_on_close` | `open_tab` opens nothing; first run opens exactly one; close returns to baseline |
| `each_tab_has_its_own_active_database` | `SELECT DATABASE()` differs per tab — the server agrees, not just our bookkeeping |
| `a_use_in_one_tabs_script_does_not_move_another_tab` | A bare `USE` stays local to its tab |
| `a_reaped_tab_connection_is_reopened_transparently` | `KILL` the connection; next run reconnects **and lands back in the tab's database** |
| `disconnect_releases_every_tab_connection` | No tab connection outlives disconnect |

**Corrections made during implementation:**

- **The Stage 0 cache test stopped proving anything.** It worked by dropping the
  exec connection and checking a schema read still succeeded — but introspection
  now runs on the *meta* connection, so that proved nothing at all. Replaced with
  an `introspection_count` on `ServerConn`: the cache's job is to keep
  information_schema round trips flat, so the test asserts on the counter
  directly instead of inferring it.
- **`ConnInfo.connection_id` was removed.** Connecting no longer opens an exec
  connection, so there is no id to report at connect time. It moved to
  `TabStatus`, where it is `0` until that tab first runs — which the test now
  asserts, turning a dropped field into a laziness check.
- **`ServerConn` is behind an `Arc`, not just a `Mutex`.** Holding the `conn`
  guard while awaiting a `KILL` would block every other consumer of server
  state. Same clone-the-Arc-and-drop-the-guard rule as the tabs map.

### Phase 2 — what shipped

File layer complete, 15 unit tests. What the plan called for, plus what
implementing it added:

| Guard | Test |
|---|---|
| Extension → dialect via the registry, unknown falls back to default | `extension_maps_to_dialect_via_the_registry` |
| Refuse > 25 MB, with a message saying to use the mysql CLI instead | `refuses_a_file_over_the_size_limit` |

| A changed-on-disk file is never clobbered, and the other edit survives | `refuses_to_clobber_a_file_that_changed_on_disk` |
| A directory is a readable error, not a panic | `reading_a_directory_is_a_readable_error_not_a_panic` |
| Atomic write leaves no temp file behind | `atomic_write_leaves_no_temp_file_behind` |

**Decisions made while implementing:**

- **`tauri-plugin-fs` is not a dependency.** It exists to expose the filesystem
  to *JavaScript*; all our file I/O is in Rust, so it buys nothing and widens
  the attack surface. (It still arrives transitively via the dialog plugin —
  same permissive licence, but we never call it.) No npm plugin packages are
  needed either, because the dialogs are driven from Rust.
- **Dialogs run in Rust, not the frontend.** `open_file_dialog` picks *and*
  reads in one round trip, so there is never a moment where the frontend holds
  a path it has not managed to read. `dialog:default` is granted anyway — it
  validated against the generated ACL, and it future-proofs any frontend use.
- **Contents are LF-normalised on open.** CodeMirror counts `\r\n` as two
  characters, so leaving CRLF in the buffer would put every byte offset from the
  splitter out of step with editor positions — the same class of bug as the
  byte-vs-UTF-16 conversion. The original ending is recorded and restored on
  save, and `restore_newlines` is idempotent so a buffer that already contains
  CRLF cannot become `\r\r\n`.
- **Writes are atomic** (sibling temp file + rename). A crash mid-write cannot
  leave a truncated script where a working one was.
- **Signatures drifted from §3, deliberately:** `save_file` also takes
  `line_ending`, and `save_file_dialog` returns a `SavedFile { path, name,
  mtime_ms }` rather than a bare path — the tab needs the name to retitle
  itself and the mtime to seed its next conflict check.

### Phases 3-4 — what shipped

New `src/tabs.ts` owns the tab model and bar; `ResultView` became stateless with
respect to results, which now live on the tab.

**Things implementation forced us to get right:**

- **CodeMirror compartments are per-`EditorState`, not per-view.** Swapping in
  another tab's state brings that state's *original* schema and lint
  configuration with it, so both are re-applied on every tab switch. Miss this
  and autocomplete silently goes stale the moment you change tabs — with no
  error to notice.
- **Dirtiness compares `Text` objects, not strings.** `doc.eq(baseline)` is a
  tree compare that short-circuits; building `doc.toString()` on every keystroke
  would be O(n) per character on a file-sized buffer. This is also why baseline
  is stored as `Text` rather than `string`.
- **`stash()` before every state swap.** The live buffer lives in the view, not
  the tab, so any operation that re-renders or switches must copy
  `view.state` back onto the outgoing tab first — including closing a
  *background* tab, where it is easy to forget.
- **A result that arrives after you switched tabs paints nothing.** `run()`
  re-checks which tab is active before touching the DOM; the result is always
  stored on its own tab regardless.
- **The dirty marker is one CSS-driven glyph**, not a separate dot and button:
  × normally, • when dirty, × again on hover — so the unsaved indicator can
  never hide the close affordance.
- **Phase 6 partially landed early:** the tab bar already shows a spinner for a
  background tab that is still running, and Run/Cancel already reflect only the
  focused tab.

### Phase 5 — what shipped

`src/files.ts` owns open/save and the prompts. Test fixtures for the manual
click-through live in `dev/samples/`, guarded by `tests/sample_files.rs` so an
editor or checkout cannot silently normalise them out of usefulness.

**Decisions made while implementing:**

- **`core:window:allow-destroy` had to be granted explicitly.** `core:default`
  covers window *getters*, not `destroy` — and `onCloseRequested` calls
  `destroy()` whenever the handler does not `preventDefault`. Without the grant
  the unsaved-changes guard would have left the window unclosable. Found by
  checking the generated ACL rather than at runtime.
- **Drag-and-drop must use Tauri's webview event.** Tauri intercepts drag-and-drop
  below the DOM, so HTML5 `drop` handlers never fire. `getCurrentWebview()
  .onDragDropEvent()` is the only way to receive them.
- **The save baseline is snapshotted *before* the write, not after.** Anything
  typed while the file is being written is a genuine unsaved change and must
  keep the tab dirty; taking the baseline afterwards would silently swallow it.
- **One file never opens into two tabs.** Opening an already-open path focuses
  the existing tab instead. Two tabs on one file would race each other's saves
  and the last writer would quietly win.
- **An empty untitled tab is reused** rather than leaving a blank tab behind
  every time a file is opened.
- **Escape and backdrop dismissal mean Cancel, never "go ahead".** Every prompt
  resolves to `null` on dismissal and callers treat that as "do nothing".
- **Save As clears the lossy flag.** A copy we wrote is valid UTF-8 whatever the
  source was, so Save becomes available on the new file.
- **A `file-note` chip in the editor header** states "invalid UTF-8 · Save
  disabled" (and CRLF) for the active tab, so the restriction is visible before
  someone tries to save rather than only in the dialog afterwards.

### Bug found during the N5 click-through (2026-09-05) — fixed and confirmed

**Switching back to a still-running tab showed its previous result set.**

The running indicator was written straight into the results pane as a transient
message when a run started. It was never recorded on the tab — so on switching
away and back, the pane re-rendered from `tab.result`, which still held the
*previous* run's rows. Stale data displayed as if current, with a query still
in flight, and no hint anything was wrong.

The tests did not catch it because they exercise the backend; this was purely a
frontend state-modelling mistake, and only a human switching tabs mid-query
would see it.

**Fix:** everything the results pane can show is now tab state, rendered in
priority order — `busy` → `error` → `result` → empty. Two things fell out of
that:

- Clearing `busy` had to move *before* the completion paint. `showResults`
  renders the running state while the flag is set, so painting first would have
  left "Running…" sitting over finished rows — the mirror image of the original
  bug.
- **Errors had the identical defect.** A failed run's message was equally
  transient, so switching away and back silently lost it and showed "No results
  yet". `tab.error` now holds it, so a failure survives a tab switch too. Same
  root cause, found only by re-reading the path while fixing the first.

The general lesson, worth carrying into Stage 2: *anything the user can switch
away from and back to must be state on the thing they switched away from, not a
side effect of whatever was focused when it happened.*

### Phases 6-7 — measurements, and what they decided

**Measured before choosing anything** (`cargo test --release --test perf --
--ignored --nocapture`, plus a JSON round trip for the IPC half). A lint pass
costs `IPC(serialise the whole document) + Rust(scan it)`:

| Buffer | Statements | `split` | `mask` | `lint` | IPC (JSON) | **Total per pass** |
|---|---|---|---|---|---|---|
| 64 KB | 564 | 0.3 ms | 0.4 ms | 2.4 ms | 1.0 ms | **~3 ms** |
| 256 KB | 2,256 | 1.0 ms | 0.8 ms | 7.0 ms | 1.5 ms | **~9 ms** |
| 1 MB | 9,015 | 4.0 ms | 2.4 ms | 22.9 ms | 6.2 ms | **~29 ms** |
| 5 MB | 45,069 | 19.1 ms | 12.6 ms | 126.8 ms | 31.1 ms | **~158 ms** |

At 5 MB with the old fixed 300 ms debounce that is **over half a core spent
re-linting while you type** — which is precisely the sluggishness the risk
section predicted. The scan itself is not the problem at ordinary sizes; the
problem is doing it repeatedly over a file-sized buffer.

**What the numbers bought:**

- **Debounce scales with the buffer**, quantised to 100 ms so it reconfigures
  about every 100 KB typed rather than on every keystroke: `300 ms + 1 ms/KB`,
  capped at 1500 ms.
- **Linting stops above 2 MB**, with the reason visible in the editor header
  ("large buffer · linting off") rather than silently doing nothing. 2 MB is
  the same threshold `files.rs` already uses to flag a file as `large`, so the
  two agree by construction.
- **A second guard inside the lint source**, because the compartment may not
  have been reconfigured yet in the tick where the buffer crossed the cap.
- Deliberately *not* done: windowed or incremental linting. It would need
  statement boundaries to avoid cutting mid-string and reporting phantom
  "unterminated" errors, and the threshold makes it unnecessary — nobody
  authors a 2 MB script, they run one.

**Script-wide row ceiling.** `MAX_ROWS` caps a single statement, so Stage 0's
five-thousand-row cap still let a ten-SELECT script hold 50,000 rows — times
however many tabs are open. `MAX_SCRIPT_ROWS = 20,000` now bounds a whole
script, and exhausting the budget is reported as `truncated` rather than
quietly returning fewer rows.

**Cross-tab visibility.** The connection label now shows how many tabs are
running, and its tooltip spells out the connection arithmetic
(`N tab connections + 2 shared = N+2`), because tabs are not free on the server.

## 6. Risks / things to watch

- **Lock discipline is load-bearing, again.** Stage 0 shipped a cancel deadlock from one over-broad mutex. The `tabs` map lock is the new version of that mistake: hold it across an await and every tab serializes through it, silently undoing the entire point of this stage. Clone the `Arc` out and drop the guard.
- **Linting does not scale to file-sized buffers.** Today `lint_sql` ships the entire document over IPC every 300 ms and rescans it end to end. That is fine for a hand-typed query and bad for a 5 MB file — which is exactly what "open a .sql file" makes routine. **Phase 7 is not optional polish; it is what stops this feature making the app feel slow.**
- **Idle connections get reaped.** MySQL's `wait_timeout` defaults to 8 hours, and a tab left open overnight will find its connection gone. Without lazy reconnect the tab is permanently broken until the app restarts.
- **Connection count on shared servers.** N + 2 is cheap for one developer and less cheap if someone opens thirty tabs against a shared staging box (`max_connections` defaults to 151). Lazy creation means idle tabs cost nothing; closing a tab must actually close its connection or they leak until disconnect.
- **Session state now diverges between tabs.** A `CREATE TEMPORARY TABLE` in tab A is invisible in tab B, and each tab has its own `USE`. This is correct and matches other clients, but it *will* surprise someone. The per-tab active-database indicator is the mitigation — don't skip it.
- **Silent file corruption.** Two ways to lose someone's data: saving a lossily-decoded buffer, and clobbering a file that changed on disk. Both need explicit handling, and both are worse than any crash because they are quiet.
- **Dirty state must be honest.** Compare against the baseline text, not a "was ever edited" flag — otherwise typing a character and undoing it leaves a tab falsely dirty and trains people to dismiss the confirm prompt.
- **Cancel must stay per-tab.** A cancel that kills the wrong tab's query is worse than no cancel at all. `conn_id` is captured per tab and `KILL QUERY` must target that one.
